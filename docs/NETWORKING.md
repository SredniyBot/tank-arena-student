# Свой сетевой канал на Java 21

Сервер арены принимает управление вашим танком и выдаёт личные наблюдения. Он не пересылает произвольные сообщения между программами. Если вашему решению нужен такой обмен, это отдельная часть вашего приложения: вы выбираете участников, содержание сообщений и реакцию на них.

Здесь — ориентиры и вопросы для проектирования. Готового транспорта, протокола взаимодействия и поведения танка в комплекте нет.

## С чего начать

Сначала передайте одну короткую строку между двумя отдельными Java-программами. Обе запускаются из `main` в IDE. Получатель должен вывести отправителя и содержимое. Игровой код подключайте после того, как понятно, кто слушает порт, кто устанавливает соединение и где возникает ошибка.

Для первого варианта достаточно HTTP: JDK содержит и клиент, и небольшой сервер. У каждого участника может быть свой принимающий порт. Другой вариант — отдельное приложение одного из участников, через которое идут сообщения. Это ваш сервис, не изменение сервера арены.

| Задача                                    | Где искать                                                                                                                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отправить HTTP-запрос                     | [`HttpClient`](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html): `newBuilder`, `send`, `sendAsync`                                   |
| Указать адрес, метод, тело и срок запроса | [`HttpRequest.Builder`](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html): `uri`, `POST`, `timeout`                          |
| Принимать запросы в своём приложении      | [`HttpServer`](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html): `create`, `createContext`, `setExecutor`, `start`, `stop` |

Создавайте `HttpClient` на срок жизни сетевой службы и используйте повторно: он управляет соединениями. `send` блокирует вызывающий поток; `sendAsync` возвращает `CompletableFuture`. В обоих случаях нужен предел ожидания. Срок подключения задаётся на клиенте, срок отдельного запроса — на запросе. Один общий изменяемый `HttpRequest.Builder` не предназначен для одновременного использования разными потоками. См. документацию [клиента](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpClient.html) и [построителя запроса](https://docs.oracle.com/en/java/javase/21/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html).

`HttpServer` — небольшой HTTP-сервер из JDK, а не внутреннее API JVM. В модульном приложении ему соответствует `requires jdk.httpserver`; этот стартовый проект не использует `module-info.java`. На один путь регистрируется обработчик. Он должен ограничить размер входа, проверить запрос и закрыть обмен. [Документация сервера](https://docs.oracle.com/en/java/javase/21/docs/api/jdk.httpserver/com/sun/net/httpserver/HttpServer.html).

## Что считать сообщением

Прежде чем кодировать обработчики, запишите один пример запроса и ожидаемый ответ. Решите:

- Как различаются версия формата, вид сообщения и его данные?
- Как получатель распознаёт отправителя и новый запуск его программы?
- Может ли одно сообщение прийти дважды? Что тогда должно произойти?
- Когда сведения перестают быть полезными?
- Нужен ли ответ о получении или достаточно следующего свежего сообщения?

Возможная оболочка сообщения, **не обязательный протокол**:

```java
public record Envelope(
        int version,
        String senderId,
        String sessionId,
        long sequence,
        String roundId,
        int observedTick,
        String kind,
        String payload) {}
```

`record` не валидирует сетевые данные автоматически. Продумайте допустимую длину строк, диапазоны чисел, неизвестные виды сообщений и совместимость версий. Для структурированных данных удобнее отдельные типы, чем одна строка с ручным разделением по запятым. В SDK уже есть Jackson и `edu.arena.protocol.JsonCodec`; это возможность кодирования данных, не готовый протокол вашего приложения.

Номер `self()` — место в текущей арене, а не постоянная личность: после выхода этот слот может получить другой человек. Не используйте только номер слота как идентификатор сетевого отправителя. Отдельно храните идентификатор своей программы и её запуска. Имя в JSON само по себе не доказывает, кто прислал сообщение.

## Как связать сеть с ботом

`student.Main` вызывает `CombatApplication.run(MyBot::new)`. Этот вызов работает до выхода из арены. SDK создаёт новый `MyBot` после возрождения. Если открывать сетевой порт в конструкторе бота, новая жизнь может попытаться занять старый порт и оставить старый поток работающим.

Сетевую службу разумно создавать один раз в `Main`, перед запуском арены. Объекту бота можно передавать нужные зависимости через конструктор. При завершении приложения закрывайте сервер, клиент и исполнители; продумайте владение этими ресурсами сами.

В `decide(CombatObservation view)` нельзя ждать ответа другого компьютера. Метод должен быстро прочитать уже полученные данные и вернуть `Control`. Сетевой обработчик тоже не должен напрямую вызывать управление танком: команда отправляется через обычный цикл SDK, в общем окне управления.

Выберите способ передачи данных между потоками:

- Если нужен только последний цельный снимок, рассмотрите неизменяемое значение в [`AtomicReference`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/AtomicReference.html). Атомарная замена ссылки не делает вложенный изменяемый `ArrayList` безопасным — публикуйте независимые неизменяемые данные.
- Если важно обработать отдельные события, рассмотрите ограниченную [`ArrayBlockingQueue`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ArrayBlockingQueue.html). Решите, что делать при переполнении. `put` может ждать свободного места; для игрового цикла обычно важнее немедленный результат `offer` и неблокирующий `poll`.

Java 21 поддерживает [виртуальные потоки](https://docs.oracle.com/en/java/javase/21/core/virtual-threads.html). Они удобны для блокирующего ввода-вывода, но не ускоряют вычисление стратегии и не отменяют ограничение числа запросов. Даже при дешёвых потоках нельзя бесконечно накапливать незавершённые обращения.

## Время и актуальность

Сервер задаёт общий физический тик. Для игры используйте `view.timing().observedTick()` и `view.roundId()`, а не сравнение настенных часов разных ноутбуков. `life()` описывает собственную жизнь вашего танка; не приписывайте этот номер чужой цели.

Придумайте срок полезности сообщения в тиках. Новый ответ не должен заменяться запоздавшим старым. При смене `roundId` сведения прежнего раунда больше не относятся к текущей ситуации. При новом запуске отправителя его счётчик `sequence` может начаться заново — для этого и полезен отдельный `sessionId`.

Если сообщения не приходят, бот всё равно должен возвращать допустимую команду. Отсутствие нового сообщения не означает, что чужой танк погиб или выполнил действие. Ответ HTTP 200 тоже не доказывает, что программа другой стороны уже использовала переданные сведения.

## Два компьютера

1. На одном компьютере начните с `127.0.0.1` и двух разных портов, например 9101 и 9102.
2. Для второго ноутбука используйте его адрес в вашей локальной сети. `localhost` всегда обозначает собственный компьютер.
3. Приёмник должен слушать нужный сетевой интерфейс, а не только loopback. Не используйте `0.0.0.0` как адрес получателя: это адрес привязки сервера.
4. Разрешите вход только на выбранный порт в используемом профиле брандмауэра. Полностью отключать брандмауэр не требуется.
5. Доступ к общему игровому серверу не доказывает доступность ноутбуков друг для друга. Гостевой Wi-Fi может изолировать устройства; NAT мешает прямым входящим подключениям через интернет. В таком случае выбирайте доступный общий узел для своей службы сообщений или согласованную локальную сеть.

Используйте только согласованные адреса. Токен арены и административный ключ не должны уходить другому клиенту. Для своего канала задавайте отдельные ограничения доступа. Не десериализуйте произвольные Java-объекты из сети; принимайте ограниченный по размеру формат данных с известными полями. Размер очереди, число отправителей, частота запросов и размер тела тоже должны иметь предел.

## Если хочется другой транспорт

[`DatagramSocket`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/DatagramSocket.html) позволяет отправлять и принимать UDP-пакеты. Они могут потеряться, прийти повторно или в другом порядке; это нужно учитывать в протоколе. Такой вариант может подойти для частых коротких обновлений, где новое значение заменяет старое. Для первого работающего обмена HTTP обычно проще наблюдать и диагностировать.

## Признаки, что решение становится пригодным

- Две отдельные программы обмениваются данными на двух компьютерах.
- При остановке второй программы ваш бот продолжает принимать решения без ожидания.
- Повтор и запоздавшее сообщение не портят состояние.
- Перезапуск отправителя и новая жизнь танка не создают лишние потоки и не занимают порт повторно.
- Размер памяти и число ожидающих запросов не растут бесконечно.
- Из журналов понятно, какие данные реально дошли, когда и почему были использованы либо отброшены.

Какие сведения передавать, кому доверять и что с ними делать в игре — часть вашей работы. Сервер арены этих решений не принимает.
